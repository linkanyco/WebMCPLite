# WebMCPLite: 현재 대화의 명시된 휴먼 의도 증거

> 이 문서는 현재 대화에 실제로 나타난 사용자 발화와, 이 대화에서 본문 승격을 요청한 휴먼 작성 보완 댓글을 모은 전달용 증거 패킷이다. 아직 별도 저장소의 정책이나 구현 완료 기록이 아니다. 사용자 문구는 `text` 블록에 그대로 보존하고, 블록 밖의 요약·분류·후속 제안은 에이전트가 작성한 것이다. 원문에 없는 승인이나 요구사항을 만들지 않는다.
>
> 출처 범위: `H01`–`H28`은 이 채팅에서 확인 가능한 사용자 메시지다. 메시지별 영구 URL·메시지 ID·발화 시각은 제공되지 않았으므로 안정적인 H ID와 원문 첫 구절을 대화 내 대조용 로케이터로 사용한다. `H29`는 이 대화에서 본문 승격을 요청한 휴먼 작성 보완 댓글이며, 인계 과정에서 원문을 확인했다. 개별 출처는 해당 항목에 적었다.

## 읽는 방법과 권한 경계

- **직접 인용**은 휴먼의 원문이다. 질문·가설·희망·승인 여부는 각 항목에 따로 표시한다.
- **에이전트 요약**은 원문을 이해하기 위한 재서술이며 새로운 휴먼 결정이 아니다.
- 후속 구현 담당자는 구현 관례, 조사 결과, 제안과 아래 휴먼 발화를 구분한다. 특히 `setBoard`의 patch 의미, revision 충돌 제어, 원자적 batch 처리, 특정 schema/library/API는 이 대화에서 에이전트가 제안하거나 예제에 구현한 사항일 수 있으나 휴먼이 직접 지정한 세부 요구로 승격시키지 않는다.
- 마지막 요청은 **WebMCPLite에 한해서 직접 merge 허용**이다. 기존 DAEGUN ERP나 다른 저장소의 merge 권한으로 일반화하지 않는다.
- 이 패킷은 현재 채팅의 제품 방향을 전달한다. 실제 저장소의 상태, GitHub 연결, 기존 파일·정책, 공식 WebMCP API의 현재 모습은 별도 확인이 필요하다.

## H01 — AI가 쓰기 좋은 사이트의 출발점

상태: 휴먼이 제시한 최초 문제의식·아이디어.

```text
잠깐, 쉬어가는 브레인스토밍 코너,  사실그냥 어찌보면 패러다임인데, MCP가 솔직히 AI가 쓰기 좋은 API인거잖아?
AI가 쓰기 좋은 웹사이트 규약같은건 없을까?
간단하게 걍 웹사이트인데 메타에 AI에게 쓰는 편지 (너는 뭘 해주면 사용자가 좋아한다) 이런거
```

에이전트 요약: 사이트를 AI가 이해하고 사용할 수 있도록 작고 발견 가능한 안내를 제공하려는 발상이다. 시작점은 새 AI 서비스 구축이 아니라 기존 웹사이트의 사용 가능성을 높이는 것이다.

## H02 — 사람과 AI가 같은 페이지를 함께 편집하는 사용 장면

상태: 명시된 목표 사용 장면·문제.

```text
목적은 반은 그거야. 솔직히 ERP가 쉬운 툴이 아니잖아. 지금 특히나 라인시트 만드는데, 이게 영 좋은 UX가 안나오는데, 이걸 말로 명령을 내리면 좋을거 같아. 복잡하게 UI로 프리셋같은걸 만들어주기보단, 챗봇에게 시켜서 바로바로 입력해주는게 좋을꺼 같기도한데, 한마디로 AI랑 나랑 웹사이트 같이 쓰는 편집하는 상황을 가정했을때 (지금 딱 이게 쉽지 않은게 코덱스도 브라우저 컨트롤하면 속도가 느리때문에 같이 작업못해 왜냐면 코덱스도 분석해야하거든 그리고 본인도 분석하는데 시간이 걸리고) 정말 둘이서 팀뷰어 켜놓은 상태에서 내가 해볼께 네가해 이런식으로 (가능하면 보이스로) 하는 상황이 나오면 좋겠단거지
그러기 위해선 html이나 js 볼것도 없이 $("#llms").text() 만 읽으면 그냥 바로 이페이지가 뭐하는건지 지금 얘가 넣을 수 있는 데이타의 name이나 id가 뭐가 있는지 쫘라락 알 수 있으면 좋겠다는거지
```

에이전트 요약: 핵심은 사람과 AI의 공동 편집과 빠른 교대다. 음성은 가능한 경우의 희망이며, 첫 릴리스에 음성 기능을 직접 구현하라는 지시는 아니다. DOM 전체 해석보다 짧은 페이지 설명과 편집 가능한 데이터의 명확한 안내를 원한다.

## H03 — 브라우저 안에서 개발자 콘솔처럼 함수로 작업하기

상태: 휴먼의 기술적 접근 가설·가능 여부 질문.

```text
그 예로 개발자가 디버깅하면서 콘설창에 자바스크립트 써서 원하는 데이타 뽑아내거나 테스트하는것처럼 코덱스도 브라우저 컨트롤이나 옆탭에 띄워놓으면 해당 형식으로 작업을 할 수 있지?
```

에이전트 요약: 화면 좌표 조작만을 전제로 하지 않고, 현재 페이지에 노출된 JavaScript 함수를 AI가 호출하는 방식을 구상한다. 특정 제품이 항상 임의 JS 실행을 허용한다는 검증된 사실로 이 질문을 바꾸지 않는다.

## H04 — 단순한 getter/setter와 사용 매뉴얼

상태: 명시적으로 제시한 설계 방향·예시. 정확한 제품 API 계약은 아직 아님.

```text
내가 제이쿼리에 익숙해서 제이쿼리 쓰는거지 당연히 자바스크립트도 가능하지.
간단하게 즉, ai한테 메뉴얼 제공해주는거에 다음과 같은 식으로 제공하는거지 
라인시트 정보 가져오는 함수 get_sheet(index=-1) -1인경우 전부 리턴 json
그리고 set_sheet(index,json)하면 전부 수정가능하게 해놓고, ai한테 이거 쓰는법 오픈
ai 는 사실상 브라우저 거의 신경도 안쓰고 js명령어만으로 컨트롤 가능 어때?
```

에이전트 요약: jQuery는 개인적으로 익숙한 표현 수단일 뿐 필수 의존성이 아니다. 적은 수의 도메인 getter/setter와 그 사용법을 명확히 공개해 AI가 편집하도록 하는 방향이다. `-1`과 함수명은 라인시트 아이디어의 구체적 예시이며 모든 예제의 보편 API로 강제됐다는 뜻은 아니다.

## H05 — 외부 브라우저 에이전트로 시작하고 나중의 챗봇도 가능하게

상태: 사용 채널에 대한 의도·확장 가능성.

```text
ㅇㅇ 이걸 그냥 코덱스 브라우저 유즈 기능을 이용해서 쓰게해도 되고, 아님 나중에 챗봇을 붙여줘도 어렵지 않게 챗봇이 작업하게 할 수도 있고.. 이거 30분만에 만든 아이디어 치고는 너무 강력한데?
```

에이전트 요약: 현재 사용하는 AI 브라우저 도구로도 활용할 수 있고, 나중에 별도 챗봇을 연결할 여지도 있어야 한다. 자체 챗봇이 선행 조건이라는 요구는 없다.

## H06 — 짧은 안내와 URL별 추가 안내, 도구 제공에 집중

상태: 단순화에 관한 반복된 휴먼 문제의식·질문.

```text
아 그럼 우리가 이야기한거랑 상당히 컨셉이 같은거네? 근데 이게 예로 사실 아까 이야기한것처럼 솔직히 이야기해서 이페이지에서 ai에게 필요한 메뉴얼은 어디야 혹은 이사이트의 메뉴얼은 어디고 url에 따라서 뭘 더 봐 이런식으로만 해주고 그냥 도구만 제공해주면 되는거지, 커먼js가 있어야하고 논문급으로 써야하나? 하긴 논문도 아이디어 하나 듣기만해도 이해할만한걸 가지고서 검증한다고 몇페이지씩 말을 키우긴한다만
```

```text
ㅇㅇ 그러니깐 "도구를 발견하고 호출하는 공통 형식" 이 복잡할 필요가 있냐는거야 내말은 사이트가 말이 길어보여서 컨셉이 사실 간단한데, (하긴 뭐 상황이 여러 상황이 있을 수 있는거 다 설명해주는걸 수도 있지만) 아직 정식이된것도 아닌데 따라가면 구지 무거워지는게 아닌가 싶기도해서
```

에이전트 요약: 공통의 도구 발견·호출 형식과 필요한 안내를 작은 규모로 제공하려 한다. 사이트 전체 설명과 현재 URL별 설명의 관계도 고려한다. 장문의 문서나 공통 코드 자체를 금지한 것은 아니며, 실익 없는 무거움을 경계한다.

## H07 — WebMCP 형식 정렬에 동의하되 규모를 작게

상태: 당시 대화에서 형식을 맞추는 방향에 대한 명시된 동의. 뒤의 H26에서 더 구체화됨.

```text
어 난 그걸 물어본거야. 기왕할꺼 맞출까? 아님 득보다 실이 많고 진짜 나중에 표준이되면 그때 변경해도 어렵지 않을꺼 같다 싶으면 걍 가고 솔직히 일은 니가 하는거니깐 좀 무겁더라도 정리가 잘된게 더 좋을 ㅜㅅ도 있어 내가 이야기하는걸로 구체화하기 어려울 수도 있잖아
```

```text
어 형식에 맞춰서 한다 정도로하자 그정도로도 충분할테고 솔직히 1년된 프로젝트가 커밋이 150개면 그건 죽은프로젝트야 ㅋㅋㅋㅋ
```

에이전트 요약: “가벼움”만을 위해 정돈된 구조를 배제하지 않으며, WebMCP 형식을 맞추는 정도에 동의했다. 두 번째 발화의 프로젝트 나이·커밋 수·활성도 평가는 당시 휴먼의 의견이며 조사로 확정된 사실이 아니다. 이를 프로젝트의 현재 상태나 공식 규격의 생존 가능성에 관한 근거로 사용하지 않는다.

## H08 — 초기 주요 업무: 라인시트와 제품 입력

상태: 사용 사례와 우선순위에 대한 휴먼 설명.

```text
어 이게 지금 솔직히 필요한게 라인시트쪽이 젤 필요하고, 제품쪽은 지들 업체 자체 데이타랑 연동시에 좋은거 같아. 
예로 제품 등록시 스타일넘버만 똭 입력해 놓고 제품 pdf 를 ai한테 던져주고 입력해줘 이런 느낌정도로 쓰이는거지 대화 핑퐁하면서 쓸건 라인시트쪽이 확실히 강해
```

에이전트 요약: 출발 업무는 라인시트 편집이며, 제품 입력은 외부 회사 자료나 PDF에서 가져온 정보를 현재 제품 양식에 입력하는 사례다. WebMCPLite 자체에 PDF 추출 모델이나 외부 시스템 연동을 구현하라는 요구는 아니다.

## H09 — 복잡한 검색을 UI에 전부 추가하지 않고 도구로 활용

상태: 확장 사용 사례. H16에서 현재 예제 범위 밖으로 명확해짐.

```text
ㅇㅇ 근데 양쪽 다 마찮가지긴해. 제품쪽도 예로 쇼피파이가 복잡한 형태로 검색이 가능하잖아? 그거 누가해 개발자나하지. 근데 그걸 구지 지저분하게 ui로 제공을 안하더라도 webmcp로 제공하면 원하는 제품만 똭 찾을 수도 있는거지
```

에이전트 요약: AI 도구를 통해 일반 UI에 모두 노출하지 않은 세부 검색 조건도 활용할 수 있다는 가능성이다. 사용자에게 숨겨진 권한이나 서버 접근을 주라는 뜻은 아니다.

## H10 — B2B 고객에게 사용 방식을 안내할 수 있음

상태: 대상 사용자와 도입 환경의 명시된 조건.

```text
아 참고로 난 b2b니깐 고객을 계몽할 수 있는 상황이야
```

에이전트 요약: 고객 교육과 정해진 AI 사용 방식을 안내할 수 있는 B2B 환경을 가정한다. 따라서 모든 소비자·모든 AI에서 무설정으로 동작해야 한다는 전제는 없다.

## H11 — 별도 번들 대 컴포넌트는 당시 열린 질문, 개발 규칙과 예제의 필요성

상태: 아키텍처 질문·의견. 최종 패키징 결정으로 취급하지 않음.

```text
흠...어찌할까? webmcp처럼 완전 별도 번들로 만들어버릴까? 아님 가볍게 컴포넌트 수준으로만 만들까?
`get_sheet` / `set_sheet` 형태로 각각 만드는건 제품 아키텍트에 룰 심어놓고 그러게 가는게 해야겠고.
흠.. 아니 사실 거의 그게 다인가? 이게 개발 룰이지 컴포넌트가 아닌가
여튼, 컴포넌트 예제 페이지 만든것처럼 예제 페이지 몇개 만들긴해야할꺼 같아. 일단 라인시트랑 비슷한 테이블 수정하기 이런 느낌으로라도
```

에이전트 요약: 개발 AI·아키텍트가 getter/setter를 일관되게 만들도록 규칙을 두고, 실제 편집 가능한 예제로 보여주고자 한다. 별도 큰 프레임워크, 특정 UI 컴포넌트 라이브러리, 단일 script 배포 중 무엇으로 고정할지는 이 발화만으로 정해지지 않았다.

## H12 — 고객이 이미 쓰는 AI의 skill/브라우저를 통한 진입 구상

상태: 구상·가능 여부 질문.

```text
근데 진짜 오픈마인드 아니냐? 첨엔 고객이 ai 잘 쓰는거에대한 두려움이 있었는데, 내가 적극 권유하는 상황이네.
그냥 고객한테 챗지피티 걍 스킬에 "브라우저탭으로 대군 사이트 열어줘, 내가 이후에 뭔가 이야기하면 메타 데이타중 agentsmd 읽고 네가 할 수 있는 작업 해줘" 이런식으로 만 박고 챗방 하나 열고 스킬한번 써줌되는거 아냐?
```

## H29 — 화면 밖 관련 객체 정보와 UI·AI의 함수 재사용

상태: 휴먼이 작성하고 이 대화에서 본문 승격을 요청한 보완 의도. 인계 과정에서 원문을 확인함.

출처: 이 대화에서 본문 승격을 요청한 휴먼 작성 보완 댓글, 2026-10-21T09:04:22Z; 인계 시 원문 확인.

```text
휴먼 코멘트 - 부가적인 정보가 있다면 기본 ui 정보 뿐만아니라 오브젝트 정보도 알고 있어야한다. 예로 아마 라인시트의 경우 제품 정보를 다 표시하지 못하고 프리뷰 팝업이나 페이지 이동등으로 제품 상세정보를 보겠지만 ai가 볼 수 있게 get_product 같은것도 존재해야한다. 
예로 제품넘버 타입이 여러개 일때 제품넘버b타입으로 표시해주ㅓ 하면 바로 작업해 줄 수 있게

get_product 같은 경우는 아마 twig나 리퀴드 같은곳에서 var produt = {% products| json %} (문법 앟아서 보고) 이런 형식으로 하면되니 어렵지 않을듯하고, 노드에선 모르겠다. 기본적으로 set_sheet의 경우엔 예로 값 받아왔을때 쓰는 함수를 그대로 이용가능하게 포장할 수 있는지 혹은 한쪽이 wrapper로 한번 감싸는등으로 최대한 재활용이 가능하게, 초기부터 코드 디자인을 이런식으로 간다 (요게 이번 작업을 미리해야하는 주요 이유)
```

에이전트 요약:

- AI가 보는 정보는 현재 화면에 표시된 필드에만 한정되지 않아야 한다. 현재 업무와 관련된 객체 정보도 조회할 수 있게 한다. 라인시트에 모든 제품 상세를 표시하지 않더라도 `get_product` 등으로 필요한 제품 정보를 제공하는 예시다.
- 제품 번호가 여러 종류일 때 “제품넘버b타입으로 표시”처럼 현재 표시 방식을 바꾸는 요청을 처리할 수 있기를 원한다. 사용자가 실제로 접근할 권한이 없는 객체까지 공개하라는 뜻으로 확장하지 않는다.
- UI가 값을 받아 반영할 때 사용하는 함수를 AI 호출에도 재사용하거나, wrapper로 연결할 수 있도록 처음부터 코드 구조를 잡는다. 별도 UI 상태와 AI 상태를 각각 관리하거나 같은 동작을 중복 구현하라는 의도가 아니다.
- Twig/Liquid와 JSON 직렬화 코드는 가능한 구현 방법을 떠올린 예시다. Twig/Liquid를 프로젝트 기술 스택으로 채택하라는 결정이나 확인된 실행 문법이 아니다. 원문의 오탈자도 직접 인용에서는 보존했다.

## 명시된 의도와 구분해야 할 에이전트 제안·미확정 사항

아래 항목은 이 패킷 작성자의 분류이며 휴먼 인용이 아니다.

1. **`setBoard`의 세부 의미**: partial patch, 전체 교체, batch atomicity, revision/expectedRevision, immutable snapshot은 휴먼이 이 대화에서 직접 명세하지 않았다. 단순하고 일관된 get/set이라는 의도 안에서 제안·검증할 설계 항목이다.
2. **저장 권한과 승인 UI**: 휴먼은 저장·취소·페이지 이동 함수를 노출하고 자동화 수준을 높일 수 있다고 했다. 모든 쓰기를 무확인 자동 실행하라고 한 것은 아니다. WebMCPLite 프로젝트에서 PR을 직접 merge해도 된다는 허용을 ERP 데이터 변경 승인과 혼동하지 않는다.
3. **음성**: 공동 작업에 가능하면 보이스를 쓰고 싶다는 의도다. 자체 음성 인식·TTS·음성 agent 서버 구축은 직접 요구되지 않았다.
4. **호스팅·전송**: AJAX는 안내 데이터 제공의 예로 나왔으나 전용 백엔드·프록시·원격 모델·자체 MCP 서버가 필수라는 결정은 없다. 기존 앱의 코드·권한·저장 경로와 어떻게 연결할지는 구현에서 검토한다.
5. **매뉴얼 진입점**: 메타데이터/`agentsmd`/`#llms`는 휴먼의 구상이다. `document.modelContext`, 도구 발견, 도구로서의 매뉴얼 함수와 어떻게 조합할지 공식 초안·지원 환경에 맞춰 제안한다. HTML 메타만 읽으면 어떤 AI든 자동으로 따른다는 보장은 없다.
6. **이름 표기**: 발상 단계 `WebMCP Lite`에서 현재 등록 프로젝트명 `WebMCPLite`로 이어졌다. 이미 등록된 프로젝트 이름을 우선 식별자로 사용하되 npm·도메인·상표 가용성은 확인된 사실이 아니다.
7. **예제 5~6개의 세부 선택**: 단일 제품, 벌크 제품, 라인시트와 비슷한 테이블 편집은 휴먼이 직접 언급했다. 나머지 예제 종류·개수별 상세 범위는 AP 계획으로 표시한다. 복잡한 hidden search/filter는 미래 가능성으로만 기록하고 현재 예제에 넣지 않는다.
8. **AGENTS 하네스와 런타임 매뉴얼**: 개발 AI가 사이트에 기능을 넣는 규칙과, 사이트를 사용하는 AI가 읽는 현재 페이지/사이트 설명을 구별하자는 구체적 설명은 에이전트 정리다. 휴먼은 둘 모두에 해당하는 필요를 각각 말했다(H12·H21·H26).
9. **기존 Kit·framework와 차별성**: 가벼운 연결, 도구 공개, 사이트 매뉴얼만으로 고유한 발명이라고 주장하지 않는다. 조사 결과와 실제 비교 범위를 별도 출처로 남기고, 사람·AI 공동 편집 경험을 얼마나 더 잘 전달하는지 검증한다.
10. **반복 검토의 종료 기준**: 지속적으로 새 세션 리뷰를 하라는 요청은 독립 리뷰를 실질적으로 수행하라는 뜻으로 보존한다. 무한 리뷰·무한 이슈 생성·근거 없는 방향 변경을 요구한 것으로 해석하지 않는다. 반복 주기와 체크포인트는 후속 계획에서 명확히 한다.
