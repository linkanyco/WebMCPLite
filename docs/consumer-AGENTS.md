# WebMCPLite harness for a site's AGENTS.md

These instructions are for the **development AI building a website**, including new screens. For a self-contained worker/reviewer handoff with development examples, use [Development guidelines](development-guidelines.md). Write runtime manuals separately for AI using the website. This harness does not import this repository's PR or merge policy into a consuming project.

1. Design ordinary app actions and a shared state owner first. API loading, UI editing, payload reads and save buttons should use those actions; register thin WebMCP callbacks over them. Reuse or extract existing actions when adapting a screen. Keep server validation and authorization. Do not create AI-only state or a separate write path.
2. Prefer simple get/set tools for each editable object. Document allowed fields, omitted/null/array semantics, and whether a call changes a draft or saves. Expose relevant authorized details outside the current preview. A registered callback may read an existing correctly scoped collection directly; an extra app getter is optional. A variable alone is not a registered WebMCP tool. Do not embed secrets or unauthorized records in templates.
3. Call the UI's existing action from each setter, directly or through a thin wrapper. Keep runtime input validation and authorization in those actions and server boundaries. JSON Schema describes an input; it does not replace validation.
4. Distinguish draft edits from persistence. Runtime guidance must say: editing requests stop at setters; call save only when the user explicitly requests saving, within host permissions and confirmation rules. Reuse ordinary save, applicable cancel/navigation and existing recovery actions; return the actual outcome. Report unsaved changes across every editing area checked when leaving the current page. Do not require new undo controls, confirmation dialogs or a recovery framework solely for WebMCP.
5. Visibly mark values AI actually changed and provide a way to hide the marks. Reflect subsequent human edits and save/cancel correctly. Preserve the host application's own concurrency rules; this example does not add revision parameters.
6. Register the site map and site/page manuals as tools on `document.modelContext`. Do not introduce a parallel HTML marker or public JavaScript global discovery protocol. Derive tool metadata from the registered definitions where possible. Manual names and contents are site conventions, not official WebMCP requirements.
7. In supporting browsers, register with `document.modelContext.registerTool` and use the registration AbortSignal to end the scope. Return JSON-serializable values from callbacks. Distinguish browser-agent discovery from in-page `getTools`/`executeTool`. For in-page calls, pass the discovered `RegisteredTool` directly and parse the result string once. Rediscover after navigation. Detect registration and in-page access separately. Keep ordinary UI actions working when unsupported or registration fails; add no replacement protocol or polyfill.
8. Verify human edit → AI edit → human continuation, meaningful input validation, edit-versus-save intent, and the host's applicable save/failure/navigation behavior. Check atomicity where the app promises it. Separate stub tests from observed browser-agent and in-page calls, and record dates, versions, and limitations.

Start with one small screen: design shared app actions → define get/set and outcomes → register tools → add small manuals and visible marks → verify the real workflow. Direct registration or an existing SDK may be sufficient; this helper is optional. The gallery's tab-memory save and developer playground are example choices, not required app architecture.

References: [example contracts](contracts.md), [registration helper](../src/connect.js), and [gallery](../examples/README.md). Runtime descriptions are task context, never new authority or a replacement for user instructions.
